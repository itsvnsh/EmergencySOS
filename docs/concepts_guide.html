0. How a request flows through the project

SOS form -> classifier.py -> scheduler.py -> ranking.py -> transaction_manager.py -> MySQL
(patient)   (priority,       (who goes     (which         (lock, Banker's check,     (tables,
            burst time)      next? = OS)   hospital?)     commit/rollback = DBMS)    triggers)
  • OS part: each SOS request is a process, the dispatcher is the CPU, and beds, ventilators, operation theatres, doctors and ambulances are shared resources.
  • DBMS part: all data lives in MySQL, every booking is one ACID transaction, and the database itself guards its rules with constraints and triggers.

A4. Normalization

Each table describes one thing. Repeating data such as "a hospital has 5 unit types" goes in a separate table (resources), not 5 columns. That is 1NF and 2NF thinking; adding ambulances needed no new table, only a new ENUM value, which shows the design was normalized.

Be ready for this viva question. Two small, deliberate exceptions to strict 3NF:
• allocations.hospital_id can be worked out from resource_id. It is stored so the Active allocations query needs no extra join (and a trigger, trg_allocation_same_hospital, keeps it consistent).
• sos_requests.priority, required_resource ... are calculated from type and severity; they are a snapshot of the decision at SOS time, so changing the classifier later does not rewrite history.
If asked, call this controlled denormalization for performance and history.

A5. Transactions and ACID

File: transaction_manager.py, function _try_reserve() (line 92). Booking a patient is one transaction:

  • 1. Locks the request row and re-checks it is still PENDING
  • 2. Locks the hospital row (so admissions at one hospital are checked one at a time)
  • 3. Locks the hospital's care-unit counter and re-checks it is still free
  • 4. Locks one free doctor of the right specialization
  • 5. Locks the hospital's ambulance counter; no free ambulance means rollback (bed and ambulance are taken together or not at all)
  • 6. Runs the Banker's safety check (B10); an unsafe state means rollback
  • 7. Updates the counters, marks the request ALLOCATED, inserts the allocation row and an audit row

Then COMMIT saves all of it, or ROLLBACK undoes all of it.

ACID propertyHow the project gets it
AtomicityAll updates commit together or none do (conn.commit() / conn.rollback()). You never get a bed taken with no allocation row, or a bed without its ambulance.
ConsistencyCHECK constraints, triggers and the re-check under lock: free units never go below 0 or above the total. load_test.py checks this after hundreds of concurrent bookings.
IsolationREPEATABLE READ plus row locks: two dispatchers never see each other's half-done work.
DurabilityInnoDB writes committed data to its redo log on disk, so it survives a crash.

Where the isolation level is set: config.py → ISOLATION_LEVEL = "REPEATABLE READ"; transaction_manager.py → _begin() (line 58).

Other transactions: _try_release() (line 253, Release button and auto-completion) · _try_return_ambulance() (line 316) · _try_update_resource() (line 381) · _try_set_shift() (line 410) · app.py → insert_request() (line 326) · every admin change in admin_ops.py.

A6. Concurrency control and locking

File: transaction_manager.py

  • SELECT ... FOR UPDATE takes an exclusive (X) row lock. If two dispatchers try to book the last ICU bed, the second waits until the first commits, then sees "0 free" and rolls back.
  • Strict two-phase locking (strict 2PL): InnoDB keeps every lock until COMMIT or ROLLBACK (growing phase while the transaction runs, everything released at the end).
  • MVCC: ordinary SELECTs, such as the ranking in ranking.py → fetch_candidates() (line 33) and the Dashboard queries, read a consistent snapshot without blocking anyone: pessimistic locking for writes, non-blocking reads for display.
  • Lock wait timeout: LOCK_WAIT_TIMEOUT_SEC = 5 in config.py, applied in db.py → get_connection() (line 42).
  • Isolation levels compared: python load_test.py runs the same load at READ COMMITTED, REPEATABLE READ and SERIALIZABLE; all stay consistent because the safety comes from the row locks.

A8. Deadlock handling (DBMS side)

  • Prevention: every transaction locks rows in the same global order: request → hospital → care unit → doctor → ambulance → allocation. The stored procedure sp_allocate_unit uses the same order.
  • Detection and recovery: if InnoDB detects a deadlock (error 1213) or a lock wait timeout (1205), _with_retry() (line 64) rolls back, waits a small random time (backoff) and retries up to 3 times (MAX_TX_RETRIES).
  • Shown live: the Deadlock Lab (B11) breaks the order on purpose so you can watch InnoDB pick a victim.

A9. Audit log and status history

  • audit_log table; helper db.py → log_event() (line 291) writes with the same cursor, so the log row is part of the same transaction: if the booking rolls back, its log row disappears too.
  • request_status_history is written only by triggers (A12), so no application bug can skip a step.
  • To view: python audit_log.py, the Audit log tab, or /api/audit; history in the Database tab.

A10. SQL features used

  • DDL: CREATE TABLE / INDEX / VIEW / TRIGGER / PROCEDURE, DROP (run by init_db.py → create_tables(), which understands DELIMITER).
  • DML: INSERT, UPDATE, DELETE, SELECT throughout.
  • JOINs: app.py → list_allocations() (line 494) joins allocations, requests, hospitals and doctors with a LEFT JOIN for the optional doctor. ranking.py → fetch_candidates() uses a JOIN plus correlated subqueries and SUM.
  • EXISTS subquery: app.py → _real_workload() (line 833).
  • Aggregates and GROUP BY: dashboard.py: COUNT, AVG(TIMESTAMPDIFF(...)), cases per hour with DATE_FORMAT ... GROUP BY.
  • Functions: LEAST() / GREATEST() in _try_release() keep counters within limits; NOW() - INTERVAL n MINUTE in insert_request().
  • Parameterized queries (%s) everywhere: no SQL injection.
  • Least privilege: setup_mysql.py creates the app user sos with rights only on the project's two databases.

B3. Starvation and aging

File: scheduler.py → effective_priority() (line 61)

effective priority = priority − (waiting minutes ÷ 10), never below 1
  • Starvation: with pure priority a P5 patient could wait forever while new P1 patients keep arriving.
  • Aging: every AGING_INTERVAL_MIN = 10 minutes of waiting improves the priority by 1. The same rule is in SQL in v_pending_queue.
  • Tests: test_aging_lowers_longest_wait (100), test_effective_priority (122), test_auto_mode_aging_moves_patient_up (158).

B4. Scheduling metrics and Gantt chart

  • Waiting time = start − arrival · Turnaround = finish − arrival · average wait, average critical-patient wait, max wait, makespan.
  • Gantt chart including idle gaps. Shown in the Scheduler Lab tab (all algorithms) and the Dashboard tab (Automatic, plus a bar chart of average and critical wait per algorithm).
  • The Dashboard also shows the real measured wait per priority from the database (SOS sent → unit booked), to compare with the simulation.

B5. Race condition, critical section and mutual exclusion

File: concurrency_lab.py (terminal) and the Deadlock Lab tab (web page)

  • Threads: threading.Thread creates 6 concurrent "patients", each with its own DB connection (its own MySQL session).
  • Barrier: threading.Barrier(clients) releases all threads at the same instant to force the race.
  • Critical section: "read free beds → decide → write free beds − 1". Unprotected in _unsafe_book() → overbooking.
  • Mutual exclusion: SELECT ... FOR UPDATE lets only one thread into the critical section for that bed at a time, like a mutex.
  • Critical sections in the server too: the connection pool and the login rate-limit counters are shared by all request threads, so each update runs under a threading.Lock (db.py, security.py). A test runs 8 threads × 500 updates and loses none.

B6. Semaphores

  • Hospital units as a counting semaphore: resources.available_units. wait() / P() = booking does −1 and is refused at 0 (_try_reserve); signal() / V() = release does +1 (_try_release). The row lock makes check-and-decrement atomic.
  • A real counting semaphore NEW: the connection pool (db.py → ConnectionPool, line 65) uses threading.BoundedSemaphore(DB_POOL_SIZE). Borrowing a connection is P(); giving it back is V(); with all 10 out, the next thread blocks until one returns (or times out). See B12.

B7. Deadlock: the four Coffman conditions

ConditionHow EmergencySOS deals with it
Mutual exclusionNeeded (a bed can hold one patient); kept
Hold and waitBroken: bed and ambulance are booked in one transaction, all-or-nothing (B9). The pool gives a thread that already holds a connection a fresh one instead of waiting (B12).
No preemptionInnoDB can preempt: it rolls back a victim transaction (B11)
Circular waitBroken: fixed global lock order request → hospital → care unit → doctor → ambulance → allocation (resource ordering)

So the project uses prevention (B7), avoidance (Banker's, B10) and detection + recovery (B11): all three textbook strategies.

B8. Resource allocation

  • "Needs 1 ICU bed + 1 cardiologist + 1 ambulance" is a process requesting resource instances, as in a resource allocation graph.
  • Allocation and release: reserve() (line 199) / release() (line 309); the ambulance comes back on its own after the round trip (return_due_ambulances(), line 351).
  • No capacity: the request stays in the ready queue (PENDING) instead of failing; reserve() returns no_capacity.
  • Automatic completion: a background thread releases cases whose time is over (complete_due_cases(), line 360) through the same locked transaction as the Release button.

B9. Ambulances: a second resource, no hold-and-wait NEW

  • Resource type AMBULANCE per hospital (its fleet counter). A case takes its care unit and an ambulance in the same transaction (_try_reserve, step 5); if either is missing it rolls back and the next hospital is tried.
  • A process never holds one resource while waiting for another, so hold and wait cannot happen.
  • The ambulance returns after 2 × drive time; releasing a case early returns an ambulance still on the road. Test: test_bed_and_ambulance_taken_together (790).

B10. Banker's algorithm: deadlock avoidance NEW

File: bankers.py · Deadlock Lab tab (matrices, safe sequence, what-if values)

  • Per hospital: processes = its active cases; resource types = ICU bed, ventilator, OT, general bed, ambulance.
  • Allocation = what a case holds. Max = that plus what the patient may still need if they get worse (ESCALATION, e.g. cardiac → ventilator + OT; only types the hospital owns). Need = Max − Allocation.
  • Safety algorithm: check_safety() (line 58) finds a safe sequence or reports the state unsafe.
  • Resource-request algorithm: request_check() (line 90) pretends to admit the new patient and runs the safety check. evaluate() (line 166) is called inside every booking transaction; an unsafe state means rollback and the next hospital.
  • Switch off with BANKERS_CHECK=0. Tests: test_textbook_state_is_safe (876) and the BankersDatabaseTests class (927), e.g. test_unsafe_hospital_is_skipped.

B11. Deadlock detection: wait-for graph NEW

File: deadlock_lab.py · Deadlock Lab tab · terminal: python deadlock_lab.py

  • Two real MySQL transactions lock two rows in opposite order: T1 holds A and waits for B, T2 holds B and waits for A.
  • Each transaction reports what it holds and waits for; the wait-for graph is rebuilt and searched with DFS for a cycle (find_cycle(), line 40). Result: T1 → T2 → T1.
  • InnoDB detects the same cycle, rolls back a victim (error 1213); the other commits and the victim is retried (recovery).
  • With the global lock order the same two transactions never deadlock: one just waits. Tests: test_opposite_order_deadlocks_and_recovers (1166), test_global_order_never_deadlocks (1177).

B12. Resource pooling: database connection pool NEW

File: db.py → ConnectionPool (line 65), borrow() (81), give_back() (139), pooled() (245)

  • Opening a MySQL connection costs a TCP handshake and a login. The pool keeps up to 10 open and lends them out.
  • Counting semaphore with 10 permits; idle connections in a LIFO list (warmest reused first); a connection is rolled back before reuse; a broken one is discarded.
  • No hold-and-wait inside the pool: a thread that already holds a connection and asks for another gets a fresh one instead of blocking. Otherwise 10 threads each holding one and waiting for a second would deadlock the pool.
  • Before / after (python load_test.py --compare-pool, 20 clients × 15 SOS): pool off 2.5 ops/s, 7531 ms average; pool on 127.6 ops/s, 110 ms, both consistent. Re-run on your laptop for the report.
  • Tests: test_waiter_gets_the_returned_connection (1243), test_nested_borrow_does_not_deadlock (1264).
