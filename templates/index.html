Automatic mode

You don't pick an algorithm. Each waiting patient is put in a queue by how serious they are, and each queue uses the algorithm that suits it:

Critical P1–P2Priority with aging
Urgent P3Shortest Job First
Routine P4–P5First Come First Served

Critical is always served first, then Urgent, then Routine. A patient who waits too long is aged up into a higher queue, so nobody waits forever. Then the ranking module picks the hospital and the transaction manager reserves the unit.

Banker's algorithm deadlock avoidance

Each hospital is a system. Its active cases are the processes; ICU beds, ventilators, operation theatres, general beds and ambulances are the resource types. A case holds one unit of its type plus the ambulance while it is on the road, and may still need more if the patient gets worse (its Max claim). Before every admission the dispatcher runs the safety algorithm and admits the patient only if a safe sequence still exists.

What if fewer units were free? (pretend only, nothing changes in the database)

Deadlock detection wait-for graph on real MySQL locks

Two transactions both need row A (the lab hospital's ICU-bed counter) and row B (its ambulance counter), the same two rows a real booking locks. In opposite order each one holds one row and waits for the other: a cycle in the wait-for graph. Our detector finds it with depth-first search, InnoDB rolls back a victim, and the victim is retried. With the project's global lock order one simply waits.

Race condition mutual exclusion: 6 patients, 1 ICU bed

All clients start at the same instant and try to book the lab hospital's last ICU bed. Without locks every client reads "1 free" and books it (lost update). With SELECT ... FOR UPDATE, written in Python or as the stored procedure sp_allocate_unit, exactly one wins and the rest roll back.
